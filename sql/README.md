# AutoCare SQL walkthrough

This directory contains the complete MySQL side of AutoCare: the normalized schema, realistic demonstration data, reusable views, stored procedures, triggers, transaction examples, analytical queries, and the database routines called by the Next.js API. MySQL is the system of record because customers, vehicles, appointments, mechanics, stock usage, and invoices are strongly related data that need foreign keys and atomic updates. Chroma complements this database for meaning-based note retrieval, but it stores only a rebuildable search index; authoritative appointment and billing data always comes back from MySQL.

## Installation order

Run the installer from the repository root so its relative `SOURCE` paths resolve:

```bash
mysql -u root -p < sql/00_install_all.sql
```

The installer executes `01`, `02`, `03`, `04`, `05`, `08`, `09`, and `10` in dependency order. It intentionally excludes `06_transactions_demo.sql`, because that file demonstrates both commit and rollback behavior, and `07_queries.sql`, because it includes illustrative `UPDATE` and `DELETE` statements. The local demo launcher in `scripts/start-demo.sh` runs the installer automatically only when the `autocare` database does not exist; it never replaces an existing database.

## How an application request reaches SQL

For a typical mutation, the browser sends an HTTP request to a Next.js route under `frontend/src/app/api`. The route verifies the signed session and role, validates input, checks ownership where necessary, and passes values to `frontend/src/lib/db.ts`, which uses parameterized placeholders. Simple reads execute fixed `SELECT` statements or query one of the views below. Multi-table or rule-heavy writes call a stored procedure; that procedure starts a transaction when several changes must succeed together, while constraints and triggers enforce invariants regardless of which client issued the SQL. MySQL errors raised with `SIGNAL`, or by a key/check constraint, return through the database helper and are mapped to an appropriate API response. Semantic search follows a related path: Chroma returns appointment IDs, and the search route joins those IDs to `vw_service_history`; if the vector service is unavailable, the route runs the MySQL `FULLTEXT` query instead.

## `00_install_all.sql` — deterministic installer

This is the orchestration file for a clean development or demonstration installation. It does not define objects itself; instead, it sources the schema, base data, views, core routines, triggers, later schema extensions, application procedures, and extra demonstration data in the only order in which all dependencies are available. The separation is intentional: it keeps each SQL concept easy to inspect for assessment while still providing one reliable entry point. Because `01_schema.sql` begins by dropping the `autocare` database, running this installer is destructive to an existing AutoCare database and should be treated as a reset command, not a migration. The transaction and free-form query demonstrations are deliberately left out so installation cannot unexpectedly modify demonstration state or stop at an intentionally rejected operation.

## `01_schema.sql` — core relational model

This file creates the `autocare` database and the ten central tables: users, customer and mechanic profiles, vehicles, service types, spare parts, appointments, the two many-to-many junction tables, and invoices. The `users` table is a shared authentication identity, while `customers` and `mechanics` are one-to-one role-specific extensions; this avoids duplicating names, email addresses, passwords, and account state. Appointments form the central operational record. Junction tables model mechanic assignment and part usage because both relationships are many-to-many, and `appointment_parts.price_at_use` deliberately snapshots the price so historical invoices do not change when the catalogue price changes. Primary, unique, foreign-key, enum, and check constraints protect referential and domain integrity. The extra indexes match common ownership, status, date, inventory, and specialization lookups, while the compound `FULLTEXT` index supports keyword comparison against the vector search mode.

## `02_sample_data.sql` — minimal coherent dataset

The base sample file inserts a small but connected dataset in foreign-key order: identities first, then role profiles, vehicles, service types, parts, appointments, assignments, used parts, and invoices. Its examples cover scheduled, in-progress, and completed work across petrol, diesel, electric, and motorcycle records so all three portals have meaningful content immediately after installation. Part-use rows include price snapshots and invoices contain internally consistent labour, parts, tax, and total values, which lets reports and tests exercise real joins and arithmetic instead of empty tables. Password values are intentionally bcrypt-shaped placeholders rather than usable credentials; `frontend/scripts/seed.mjs` replaces only those placeholders with genuine bcrypt hashes for the documented demo password. Keeping plaintext passwords out of SQL prevents credentials from being committed while still making the dataset repeatable.

## `03_views.sql` — stable read models

The views turn frequently repeated joins and aggregates into named, consistent read models. `vw_service_history` combines an appointment with its vehicle, customer, service type, assigned mechanic names, and invoice while preserving appointments that do not yet have assignments or billing through left joins. `vw_mechanic_workload` uses conditional aggregation for total, completed, and active work. `vw_low_stock_parts` centralizes the operational definition of low stock (`stock_qty <= reorder_level`), and `vw_revenue_by_service` summarizes frequency and revenue by service type. These abstractions are justified because customer, staff, admin, reporting, and search routes all need the same interpretations. For example, appointment screens and vector-search results query `vw_service_history`, staff workload reads `vw_mechanic_workload`, and the admin dashboard consumes the workload, low-stock, and revenue views without duplicating complex SQL in each route.

## `04_procedures.sql` — core workflows and calculation

This file introduces two foundational stored procedures and one reporting function. `sp_book_appointment` validates that the referenced vehicle and service type exist, inserts the appointment, and returns its generated ID through an output parameter; the customer booking API calls it inside an application transaction so the later priority update belongs to the same unit of work. `sp_complete_appointment_and_bill` marks an appointment complete, calculates parts from immutable usage snapshots, takes the service base price as labour, adds five percent tax, and creates or refreshes the one-to-one invoice inside a transaction. `fn_customer_lifetime_spend` returns paid invoice totals for dashboards and reports. These rules live close to the data because appointment completion and invoice arithmetic must remain consistent even if another trusted client is added later. The more restrictive application-facing finish procedure in file `09` validates workflow state before delegating to this core billing routine.

## `05_triggers.sql` — automatic cross-row invariants

These triggers protect rules that a simple column check cannot express. Before part usage is inserted, `trg_check_stock_before_part_use` reads the relevant part and rejects a quantity larger than available stock. After a successful insert, `trg_deduct_stock_after_part_use` decreases inventory; deleting that usage fires `trg_restore_stock_after_part_delete`, making corrections and cancellations reversible. `trg_award_loyalty_on_payment` adds points only on the transition into the paid state, preventing repeated updates from awarding points twice. This approach is justified because stock and loyalty correctness must not depend on a particular UI button behaving properly. In request flow, the API calls a procedure such as `sp_add_part_to_appointment`, `sp_cancel_appointment`, or `sp_pay_invoice`; the procedure performs the business operation, and these triggers run automatically within the same transaction before control returns to the API.

## `06_transactions_demo.sql` — commit and rollback proof

This file is an isolated teaching and presentation script rather than part of normal installation. Demo A creates an appointment, reserves a part, assigns a mechanic, and commits the complete group, showing how related changes become visible together. Demo B creates a temporary procedure with an exception handler, starts a transaction, inserts an appointment, and then deliberately requests 500 batteries. The stock trigger rejects that impossible quantity; the handler explicitly rolls back and the final query proves the earlier appointment insert did not leak (`should_be_zero = 0`). The explicit handler is important because SQL clients differ in whether they stop after a statement error, whereas application code must guarantee rollback deterministically. This mirrors the `try/commit` and `catch/rollback` behavior used by the database helpers and stored procedures in real requests.

## `07_queries.sql` — relational query demonstrations

The query collection demonstrates the required SQL techniques against the same production-shaped schema rather than artificial tables. It includes basic and multi-table joins, monthly aggregation, `GROUP BY` with `HAVING`, ordered totals, correlated and non-correlated subqueries, `NOT EXISTS`, view consumption, the lifetime-spend function, and MySQL natural-language `FULLTEXT` search. It ends with explicit `UPDATE` and `DELETE` examples to show the full DML set, which is why the installer does not run this file automatically. Several ideas also appear in the application’s fixed report whitelist, where users choose a known report name rather than submitting SQL. That design preserves the educational and analytical value of expressive queries without exposing an arbitrary-query or SQL-injection interface through the browser.

## `08_alter_and_extensions.sql` — schema evolution, audit, and scheduling rules

This file demonstrates how the initial model evolves after release. It adds appointment priority, last-login tracking, and a database-level note-length check; replaces a single inventory index with a composite stock/reorder index; and adds indexes for common payment-status and role filters. It also creates status and restock audit tables, then adds triggers that record every appointment state transition, prevent a mechanic from being assigned to overlapping open jobs, and prevent odometer rollback. Finally, `vw_dashboard_kpis` exposes a single-row operational summary for the admin dashboard. These features are grouped here to make `ALTER`, index replacement, auditability, and cross-row scheduling constraints visible as separate database concepts. They must run before file `09`, because application procedures write the new audit structures and rely on the added rules.

## `09_app_procedures.sql` — API-facing business operations

This file is the main mutation boundary used by the web API. Registration and staff creation atomically create both the shared user and the correct role profile and return the user ID. Assignment validates appointment and mechanic state before the overlap trigger performs the final schedule check. Start and finish procedures enforce legal status transitions, with finish delegating to the billing routine in file `04`. Part addition merges repeated quantities in a transaction while the file `05` triggers restore, validate, and re-deduct stock; removal and cancellation likewise rely on stock restoration. Payment validates invoice state and lets the loyalty trigger award points, while restocking updates inventory and its audit row together. Next.js calls these routines through the whitelisted `callProc` helpers with parameterized arguments, so the browser never assembles SQL or controls procedure names.

## `10_extra_sample_data.sql` — dashboard and semantic-search depth

The extra dataset makes the finished demo visually and semantically useful. It adds the documented administrator, distributes completed invoices across several months, and supplies distinct brake, battery, air-conditioning, EV charging, engine, and motorcycle cases. That variety feeds dashboard charts, revenue reports, pending billing, staff workload, and meaning-only vector-search examples such as matching “wall box” with a stored charging-port complaint. New appointments use `LAST_INSERT_ID()` rather than assuming fixed generated IDs. Part IDs and prices are selected into variables before inserting usage rows because an `INSERT ... SELECT` directly from `spare_parts` would conflict with the stock trigger updating the same table in MySQL. The final future-relative jobs use `NOW()` so the schedule remains demonstrable regardless of installation date.

## Practical request-flow examples

- **Customer registration:** `POST /api/auth/register` validates input and hashes the password, then calls `sp_register_customer`; its transaction creates `users` and `customers` together or neither.
- **Appointment booking:** the customer route checks vehicle ownership, calls `sp_book_appointment`, updates priority in the same application transaction, and schedules vector indexing after the response.
- **Mechanic uses a part:** the staff route checks assignment and calls `sp_add_part_to_appointment`; the procedure merges usage while stock triggers reject overselling and adjust inventory atomically.
- **Job completion:** the staff route calls `sp_finish_job`, which validates the state and delegates to `sp_complete_appointment_and_bill`; the status audit trigger records the transition and the API then reads the invoice.
- **Invoice payment:** a customer or admin route calls `sp_pay_invoice`; the payment update fires the loyalty trigger exactly once.
- **Dashboard and search:** dashboards read the views from files `03` and `08`; semantic search joins Chroma IDs back to `vw_service_history`, while keyword fallback uses the full-text index created in file `01`.
